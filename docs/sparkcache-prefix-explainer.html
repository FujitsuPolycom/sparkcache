SparkCache in SparkRing

How conversation context is stored and restored

SparkCache aligns cache identity and admission to 256-token boundaries. The current branch restores the longest exact snapshot already present on every rank; it does not yet make every 256-token boundary an independently stored prefix.

03 “256-token chunk” has two meanings

The logical geometry is shared, but the physical payload semantics differ by storage mode. This distinction determines whether prefix aliases and tail-only writes can safely reuse stored bytes.

Current per_token_rows

Each encoded chunk contains the owned tensor rows for one logical token interval.

rows A0–256
rows B256–512
rows C512–768
rows D768–1024

The payloads have prefix meaning. This is the safe first target for descriptors that reference an existing immutable trunk without copying its bytes.

Current GLM block_pages_v1

SparkCache first encodes one opaque, exact-boundary HMA page snapshot, then divides its bytes into as many files as there are 256-token logical intervals.

snapshot
headerall layer pagesall groups
on disk
byte 1/4byte 2/4byte 3/4byte 4/4

Those files are authenticated byte partitions of the whole snapshot—not token-local KV chunks. Truncating them cannot create a valid earlier GLM prefix. GLM tail-only storage needs a new page-semantic format and a distinct cache namespace.

05 Verified-or-recompute restore

Context is restored only after identity, quorum, compatibility, and chunk integrity checks pass.

Verified state or recomputation

A missing rank, malformed manifest, incompatible identity, or bad chunk hash becomes a miss. The request recomputes instead of consuming unverified KV state.

Identity stays topology-bound

Checkpoint digests, layout, TP/DCP, physical rank, chunk geometry, record schema, draft policy, and the prefix-key format remain part of the namespace.

Optional work cannot stall serving

Inventory warm-up may turn a potential reuse into recomputation. Backlog limits skip optional restores, and unrelated inference continues.

06 What is planned, not implemented

These improvements build on exact-prefix discovery, but none should be inferred from the current 256-token geometry alone.

Planned Sparse prefix descriptors

Publish bounded metadata for selected earlier prefixes that references already durable payload. The safe first implementation is per_token_rows; opaque GLM page snapshots cannot be shortened by manifest tricks.

Planned Tail-only publication

Write only state created after the longest verified prefix. Today, a growing conversation can publish another complete exact-boundary snapshot, including its existing trunk.

Planned Single-flight restore

Let one leader restore a shared digest, publish the resulting GPU blocks through vLLM, and let concurrent followers reuse those blocks. Today, concurrent same-prefix requests may each schedule external restore work.

07 GLM-5.3 TP4 evidence

The native direct-restore result is experimental performance evidence, not yet a C16 concurrency qualification.

Exact runtime

Four DGX Spark systems, GLM-5.3 Flash, TP4/DCP1, two host restore workers, two native placement lanes, and two 256 MiB mapped-host arenas per rank.

Recorded 128K restore

Each rank restored 813,068,464 bytes through four native slabs. Cache service was 131.3–250.1 ms per rank; end-to-end request latency was 0.907 s.

Correctness and remaining work

A post-restore semantic canary matched and health remained 200. C2/C8/C16 shared, mixed-trunk, unrelated-cold, and decode-interference tests remain.
